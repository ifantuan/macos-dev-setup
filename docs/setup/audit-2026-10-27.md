## P1：优先修复

### A01：清理预演在交互终端中可能真的卸载软件

- 位置：[brew-maintenance.sh](../../scripts/brew-maintenance.sh)，第 107–119 行。
- **[事实]** `--cleanup-preview` 直接运行 `brew bundle cleanup`。Homebrew 7.0.11 的实现默认询问确认；标准输入、输出均为终端且用户按 `y` 时，会进入实际清理分支。封装却承诺不会删除，并把成功退出解释为“无需清理”。
- 影响：用户执行预演后可能真实卸载清单外软件，事后提示还会失真。审计没有执行真实清理；结论由本机 `bundle/subcommand/cleanup.rb`、`ask.rb` 与[官方命令手册](https://docs.brew.sh/Manpage#bundle-subcommand)交叉核验。
- **[建议]** 预演必须强制关闭交互确认，例如将该子进程的标准输入接到 `/dev/null`，并对输出、错误和退出状态做区分。增加带终端条件的测试，保证任何输入均无法触发删除。

### A02：符号链接配置的“备份”不能保留被覆盖前的内容

- 位置：[bootstrap.sh](../../scripts/bootstrap.sh)，第 107–114、135–151 行。
- **[事实]** 备份使用 `cp -R`，在本机保留源符号链接；随后向原路径执行普通 `cp`，会穿过链接覆盖其目标。
- 隔离复现：让临时 `.zshrc` 指向另一份配置，执行 `--skip-brew` 后，外部目标已改变，备份仍指向这个已改变的目标，旧内容无法从备份恢复。
- **[建议]** 为链接定义明确策略：保存链接元数据和原始内容，或备份后原子替换链接本身；不要写穿链接。父目录为链接、悬空链接也应加入验证。

### A03：系统 Bash 3.2 下正式 quickstart 会中断

- 位置：[quickstart.sh](../../scripts/quickstart.sh)，第 66–70 行。
- **[事实]** 正式执行时 `runtime_args=()` 保持为空。在 `set -u` 下，Bash 3.2 展开空数组会产生 `runtime_args[@]: unbound variable`，返回 1。
- 影响：核心软件及配置安装结束后，运行时初始化和最终自检都不会执行。预演会给数组加入参数，因此现有 CI 的 dry-run 无法发现。
- **[建议]** 对空参数直接调用，或使用兼容 Bash 3.2 的展开方式；用 `/bin/bash` 验证非预演控制流，子操作可以用桩命令替代。

### A04：废弃的 `homebrew/bundle` tap 阻断干净机器安装

- 位置：[Brewfile](../../Brewfile) 与 [Brewfile.core](../../Brewfile.core) 第 6 行，以及两份差异示例。
- **[事实]** 四份清单均声明 `tap "homebrew/bundle"`。Bundle 已合并进 Homebrew；本机 7.0.11 的 `official_taps.rb` 将 `bundle` 列为废弃 tap，`Tap#install` 会拒绝安装。[原官方仓库](https://github.com/Homebrew/homebrew-bundle)
- 触发条件：该旧 tap 尚未安装的干净机器。Bundle 会尝试安装它并记录失败，安装整体无法成功返回；已有旧 tap 的机器可能掩盖问题。
- **[建议]** 从全部清单删除这条 tap 声明，继续直接使用内置 `brew bundle`。不能只用 `bundle list` 作为安装可行性的验证。

### A05：两条备份路径使用 Homebrew 7 已停用参数

- 位置：[sync-back.sh](../../scripts/sync-back.sh) 第 86 行；[backup-configs.sh](../../scripts/backup-configs.sh) 第 438–440 行；[包管理器手册](../runtimes/package-managers.md) 第 59 行。
- **[事实]** `brew bundle dump --describe` 在 Homebrew 7.0.11 实测返回 1。描述注释已经成为默认行为，该参数是停用而非普通警告。[官方迁移指南](https://brew.sh/7.0.0-migration-guide/#commands-and-configuration)
- 影响：`sync-back --include-brew`、选择性备份中的 `brew` 项，以及包含该项的 `--safe` 备份都会失败；前面已复制的其他配置不会回滚。`backup-configs.sh` 启用了 `set -euo pipefail`，导出失败会当场终止整个脚本，后续配置项不会处理，第 605 行的失败汇总也不会输出。
- **[建议]** 删除参数及预演、文档中的同名示例，先导出到临时文件，校验成功后再替换仓库清单。

### A06：第三方软件的信任与全局清理语义没有适配

- 位置：[Brewfile](../../Brewfile) 第 7–10、106、132 行；[brew-maintenance.sh](../../scripts/brew-maintenance.sh) 第 134 行。
- **[事实]** `zedg`、`rebased` 来自第三方 tap，使用未限定来源的短名称；清单中没有 `trusted` 声明，也没有信任前置检查。Homebrew 7 默认要求信任后才能加载第三方定义。
- **[事实]** Homebrew 7 的 Bundle 实际清理会把全局显式信任记录替换为选中 Brewfile 的声明。当前清单没有任何信任声明，清理会移除所有显式信任，包括其他清单或手工建立的记录。[官方 Bundle 信任说明](https://docs.brew.sh/Brew-Bundle-and-Brewfile#trusted)
- 影响：没有预先授权的干净机器无法加载上述第三方 cask；清理还可能影响当前 profile 以外的软件维护。此项基于源码和官方说明，未执行信任变更或第三方安装。
- **[建议]** 明确包来源；审查后优先按包声明信任，避免为整个 tap 盲目授权。清理前展示并备份信任差异；评估是否应限制公共 profile 执行全局 Bundle 清理。

**[事实]** `core` 有 3 个 tap、30 个 formula、9 个 cask；`full` 有 5 个 tap、61 个 formula、61 个 cask。未发现同类型同名重复声明，core 的所有软件条目均包含在 full 中。

2026-10-27 读取官方 formula/cask JSON 索引后的结果：

| 条目 | 核验结果 | 建议 |
|------|----------|------|
| `codex-app` | 官方标记弃用，给出的替代包是 `chatgpt`，当前 full 已含 `chatgpt` | 评估移出默认恢复集；弃用不等于已经不能安装。[官方 cask 页](https://formulae.brew.sh/cask/codex-app) |
| `sdl2` | 当前是 `sdl2-compat` 的有效别名 | 可规范名称，不应报告为失效依赖。[官方 formula 页](https://formulae.brew.sh/formula/sdl2-compat) |

| 其余可解析的官方条目 | 本次索引比对未见额外弃用或停用标记 | 这只验证软件元数据，不代表全部已通过安装、兼容或安全验证 |

**[建议]** Homebrew 7 适配完成后，可以加入以下能力：

1. 用 `brew doctor --json` 输出可归档诊断，避免仅依赖自然语言输出。
2. 单独提供 `brew vulns --brewfile=Brewfile.core --deps --json` 漏洞检查。它只覆盖 formula，不能替代 cask、SDKMAN、pyenv、npm 等渠道的审计；本次未运行漏洞扫描。
3. 使用 `brew deps --brewfile` 评估完整清单的依赖规模，再逐项判断显式声明的底层库是否确有直接用途。不要机械删除所有看似间接依赖的包。
4. 保留 Homebrew 7 默认批量安装方式，无需额外增加已被弃用的 Bundle `--jobs` 调参。
5. 分开“安装满足”和“版本最新”两种检查：默认恢复采用 `--no-upgrade`，对应验收也应采用同一策略；独立报告过期软件。

这些接口通过本机 7.0.11 源码及[官方手册](https://docs.brew.sh/Manpage)核对，不是已经接入项目的能力。

## 其他优化与文档一致性

以下属于改进建议，不与已复现的 P1/P2 混为一谈：

- **备份格式。** VS Code 原生配置允许 JSONC，但当前备份只接受标准 JSON，合成注释、尾逗号配置已验证会被拒绝。建议支持 JSONC 校验或规范化输出，不要求用户修改自己的有效配置。
- **目录快照。** Rime 使用 `cp -R` 合并目录，源目录删除的文件会残留在备份中，已隔离复现。应明确这是增量合并还是精确快照；若要精确快照，先写全新目录并验证后替换，避免未经保护直接执行带删除的同步。
- **配置保护。** `--safe` 只代表预先分类，敏感词扫描只警告；`sync-back` 没有这一步。建议共享暂存、检查和替换逻辑，保留人工差异审查。没有证据表明当前仓库含真实密钥，本次也未完成 Gitleaks 扫描。
- **临时文件。** SDKMAN 安装器使用固定 `/tmp/macos-dev-setup-sdkman-install.sh`，日志库使用 `mktemp -u` 后创建 FIFO。建议改为私有临时目录、清理 trap 和适当权限，避免并发覆盖及路径竞争；本次未模拟攻击。
- **回滚闭环。** 当前只有备份，没有统一恢复入口。建议保存普通文件、链接、原先不存在的 defaults 键等状态，增加恢复预演和恢复验证。恢复时不要误覆盖执行之后产生的新配置。
- **Shell 行为。** `.zshrc` 未将 `~/.local/bin` 加入 PATH，使用 uv 的默认 Python 命令或 pipx CLI 时需要额外处理；Homebrew 路径硬编码也应统一。`grep=rg`、`find=fd` 不是参数兼容替换，会影响直接粘贴传统命令，可改用独立别名。
- **支持范围。** 将“仓库已验证环境”与“Homebrew 上游支持等级”分开记录。Homebrew 7 已将 Intel 和 Sonoma 14 降为 Tier 3，不能据现有半恢复演练推断支持全部新系统。[官方支持等级](https://docs.brew.sh/Support-Tiers)
- **安装耗时。** 快速启动文档各阶段估时相加为 28–53 分钟；目前没有真实空机安装计时证据。建议把 30 分钟定义为目标，提供只安装所需语言的快捷入口，并分别记录软件安装、运行时编译和人工登录耗时。
- **文档漂移。** `profiles.md` 把 full 描述为含运行时、自检，与 Makefile 和 bootstrap 不一致；多处直接 `brew bundle` 示例未带 `--no-upgrade`，与默认恢复策略不同；Ghostty 配置注释写行高增加 15%，实际数值为 `2`。应统一事实源。

## 测试与实施顺序

现有 CI 的积极基础包括严格 ShellCheck/Gitleaks 开关、模板校验、临时家目录复制演练。问题在于缺少正式控制流与失败行为验证，而不是没有任何检查。

**[建议]** 按以下顺序实施，继续保留轻量 Bash 架构，不需要先引入大型配置管理框架：

| 顺序 | 交付范围 | 验收条件 |
|------|----------|----------|
| 1 | 预演安全边界、链接备份、唯一备份批次 | 终端输入不能触发删除；原始配置和原始链接都可恢复；重复执行不毁掉旧备份 |
| 2 | Bash 3.2、废弃 tap、`--describe`、第三方信任 | 系统 Bash 正式控制流通过；Homebrew 7 导出成功；干净信任状态的安装计划可解释 |
| 3 | 错误传播、原子导出、升级参数、记录 profile | 外部命令失败不伪装成功、不损坏旧文件；显式参数覆盖默认值；记录与实际范围一致 |
| 4 | 运行时基线、清单精简、支持矩阵与文档 | 安装渠道一致；旧项目可覆盖版本；文档命令和实际行为一致 |
| 5 | 干净账号或 VM 的真实恢复 | 记录所用提交、Bash/Homebrew/macOS、耗时、人工步骤、失败点及运行时可用性 |

建议 CI 补充：系统 Bash 3.2 与现代 Bash；使用桩命令执行正式 quickstart；备份链接、目录、失败输出和重复执行；敏感配置暂存；命令不存在、返回失败和非交互模式；core 是 full 子集；已停用 CLI 参数的回归检查。环境验收应与仓库静态自检分开，不能用 `zsh -n` 代替真实 Shell 启动，也不能用 `bundle list` 代替安装可行性。
